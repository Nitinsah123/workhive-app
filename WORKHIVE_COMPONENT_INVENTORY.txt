10. Inputs:

11. Outputs:
    - AuthResponse: { accessToken, refreshToken, tokenType: "Bearer", user: { id, email, fullName, role, employeeCode }, tenant: { id, name, code, timezone } }
12. Loading state:
    - Button spinner with disabled state while mutation is pending.
13. Empty state:
    - Form validation errors displayed on empty/invalid inputs.
14. Error handling:

================================================================================
SECURITY ARCHITECTURE & RISK AUDIT
================================================================================

1. Environment Variables & Secrets Handling:
   - JWT Secret: Set via `${JWT_SECRET}`. Production minimum 256-bit key.
   - Mail Password / Google App Password: Set via `${SPRING_MAIL_PASSWORD}`.
   - Google OAuth Client Secret: Set via `${GOOGLE_OAUTH_CLIENT_SECRET}`.
   - GitHub OAuth Secret: Set via `${INTEGRATIONS_GITHUB_CLIENT_SECRET}`.
   - Database Passwords: Set via `${SPRING_DATASOURCE_PASSWORD}`.
   - MinIO Secret Key: Set via `${MINIO_SECRET_KEY}`.
   - Zero hardcoded plaintext credentials in application source code.

2. Encryption at Rest:
   - OAuth access tokens and refresh tokens in `email_connections` and `integrations` are encrypted using AES-GCM (128-bit authentication tag, 12-byte random IV) via `CryptoUtils.java`.
   - Password hashes use BCrypt with standard work factor.

3. Token & Session Protection:
   - Access tokens use short-lived JWT (1 hour).
   - Refresh tokens stored in database with explicit revocation flag and 7-day expiration.
   - CSRF state protection on all OAuth flows (Gmail OAuth and GitHub OAuth) using cryptographically secure random tokens validated on callback.

4. Multi-Tenant Isolation Verification:
   - Every single database table has `tenant_id` foreign key.
   - All repository query methods require `tenantId` extracted exclusively from server-side `TenantContext`.
   - Direct API manipulation tests confirm that Tenant A cannot access Tenant B's data or email credentials even if IDs are guessed.
