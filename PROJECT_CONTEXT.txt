1. PROJECT OVERVIEW
==================================================

* Project name: WorkHive
* What problem the project solves: Provides a multi-tenant SaaS workspace platform for B2B organizations,
  enabling teams to manage projects, tasks, attendance, leave, documents, announcements,
  integrations (GitHub, Jira, GitLab, Slack), reporting, and real-time collaboration—all
  within an isolated, tenant-scoped environment.
* What the project currently does:
  - Full multi-tenant workspace with organization (tenant) onboarding
  - JWT-based authentication with access/refresh tokens
  - User management with invitations, roles (TENANT_ADMIN, MANAGER, EMPLOYEE)
  - Department and team hierarchy management
  - Project management with milestones, members, progress tracking
  - Task management with Kanban, subtasks, comments, history, review workflow
  - Attendance check-in/check-out and time tracking
  - Leave management with leave types, balances, apply/review workflow
  - Document management with MinIO object storage
  - Announcements (targeted by org/dept/team)
  - Notifications (in-app, real-time via WebSocket/STOMP)
  - Global search across users, projects, tasks, documents
  - Reports (employee, project, organization) with PDF and CSV/XLSX export
  - Integrations with GitHub (OAuth + webhooks), Jira, GitLab, Slack
  - Gmail OAuth email connections for transactional email delivery
  - Activity feed with heatmap
  - Archive and restore (soft-delete) system
  - Action center for pending approvals (leave, task reviews)
  - Organization settings
  - Audit logging with outbox events
  - Full React + TypeScript frontend with 20+ pages
* Main use case: Enterprise/B2B SaaS platform where organizations onboard their workspace,
  invite employees, and collaboratively manage daily work.
* Current status: Functionally complete MVP with both backend and frontend deployed.
  Deployed on Render (frontend static site + backend Docker) and Railway.

CORE CLASSES:
  - TenantContext: ThreadLocal holder for tenantId, userId, role. Set from JWT by filter.
  - JwtTokenProvider: Generates access/refresh tokens, validates, extracts claims.
  - JwtAuthenticationFilter: OncePerRequestFilter that extracts Bearer token, sets security context.
  - AuthUserDetails: Java record(userId, tenantId, email, role).
  - GlobalExceptionHandler: @RestControllerAdvice with handlers for all exception types.
  - CryptoUtils: AES encryption/decryption for integration access tokens.
  - DatabaseUrlEnvironmentPostProcessor: Normalizes cloud DB URLs (Render/Railway/Heroku).

DATA FLOW:
  1. HTTP request arrives at Spring Boot
  2. JwtAuthenticationFilter extracts Bearer token from Authorization header
  3. JWT is validated and claims extracted (userId, tenantId, role, email)
  4. TenantContext is set (ThreadLocal)
  5. Spring Security context is set with authorities (ROLE_TENANT_ADMIN, etc.)
  6. Request reaches @RestController
  7. @PreAuthorize checks role if applicable
  8. @Valid triggers bean validation on request body
  9. Controller delegates to Service
  10. Service uses TenantContext.requireTenantId() for tenant isolation
  11. Service calls JPA Repository (all queries are tenant-scoped)
  12. Response is serialized to JSON (Jackson, non-null properties, ISO dates)

ERROR HANDLING (GlobalExceptionHandler):
  - ResourceNotFoundException → 404 {error, message, timestamp}
  - BadRequestException → 400
  - DuplicateResourceException → 409
  - DataIntegrityViolationException → 409

  - AccessDeniedException → 403
  - SecurityException → 401
  - MethodArgumentNotValidException → 400 {error, message, fields: {field: error}}
  - MaxUploadSizeExceededException → 413
  - RateLimitException → 429
  - Generic Exception → 500

9. DATA FLOW
==================================================

Example: User creates a new task

1. User fills task form in React frontend (TasksPage.tsx)
2. Frontend calls taskApi.create(data) which sends POST /api/tasks with JSON body
3. Axios interceptor attaches Bearer JWT token to Authorization header
4. Spring Boot receives request on port 8080
5. JwtAuthenticationFilter extracts and validates the JWT
6. TenantContext is set with userId, tenantId, role from JWT claims
7. Request reaches TaskController.createTask()
8. @Valid triggers validation on CreateTaskRequest DTO
9. TaskController calls TaskService.createTask(request)
10. TaskService reads TenantContext.requireTenantId() for tenant isolation
11. TaskService creates Task entity, sets tenantId, creatorId from context
12. TaskService saves Task via TaskRepository (JPA → PostgreSQL)
13. TaskService creates subtasks if provided
14. TaskService publishes activity event via WorkActivityService
15. TaskService may create notifications for assignee
16. TaskService returns saved Task entity
17. TaskController returns ResponseEntity with 201 status and Task JSON
18. Spring serializes Task to JSON (Jackson, non-null, ISO dates)
19. Response sent back to frontend
20. Frontend receives response, React Query cache is invalidated
21. UI updates to show the new task

Example: User logs in

1. User enters email/password on LoginPage.tsx
2. Frontend calls authApi.login({ email, password })
3. POST /api/auth/login (public endpoint, no JWT required)
4. AuthController.login() → AuthService.login()
5. AuthService validates credentials (BCrypt password check)
6. AuthService generates access + refresh tokens via JwtTokenProvider
7. AuthService saves refresh token to refresh_tokens table
8. AuthService constructs AuthResponse with user info, tenant info, tokens
9. Response returned to frontend
10. Frontend authStore.setAuth(data) saves tokens to localStorage
11. Zustand state updates, isAuthenticated = true
12. React Router redirects to /dashboard

  - Automatic token refresh flow
  - Refresh token persistence in database
  - Refresh token revocation on logout

AUTHORIZATION:
  - Role-based: TENANT_ADMIN, MANAGER, EMPLOYEE
  - Spring Security @PreAuthorize annotations
  - Method-level security (@EnableMethodSecurity)
  - ProtectedRoute and AdminRoute guards in frontend

INPUT VALIDATION:
  - Jakarta Bean Validation (@NotBlank, @Email, @Size)
  - @Valid annotation on all request bodies
  - Validation error handler returns field-level errors

API SECURITY:
  - CORS with allowlist of origins
  - Stateless sessions (no cookies/session IDs)
  - 401/403 JSON error responses
  - Max upload size enforcement (50MB)
  - Rate limiting exception support (RateLimitException)
  - Request correlation IDs

SECRETS/CONFIGURATION:
  - Environment variables for all secrets
  - .env file (git-ignored)
  - .env.example template provided
  - JWT secret configurable via JWT_SECRET env var
  - Database credentials via env vars
  - OAuth credentials via env vars

16. IMPORTANT IMPLEMENTATION DETAILS
==================================================

1. TENANT ISOLATION:
   - ALL data is scoped by tenant_id. Every entity has a tenant_id field.
   - TenantContext is set from JWT claims in JwtAuthenticationFilter.
   - NEVER trust tenant info from URL, request body, or query params.
   - Services use TenantContext.requireTenantId() for every query.

2. JWT STRUCTURE:
   Access token claims: { sub: userId, tenantId, email, role, fullName, iat, exp }
   Refresh token claims: { sub: userId, tenantId, type: "refresh", jti: randomUUID, iat, exp }

3. SOFT DELETE / ARCHIVING:
   - Many entities use status field (ACTIVE, ARCHIVED, INACTIVE)
   - DELETE endpoints typically soft-delete (set status to ARCHIVED)
   - Permanent delete endpoints exist separately (/{id}/permanent)
   - Archive system provides bulk restore/permanent delete

4. OPTIMISTIC LOCKING:
   - Task entity has a 'version' field for optimistic locking
   - UpdateTaskRequest and UpdateTaskStatusRequest accept version for conflict detection

5. PAGINATION:
   - All paginated endpoints return Spring Page objects
   - Frontend expects: { content: [...], totalElements, totalPages, number, size, ... }
   - Pagination is zero-indexed

6. DATE/TIME:
   - All timestamps stored as TIMESTAMP WITH TIME ZONE in PostgreSQL
   - Dates serialized as ISO strings (Jackson: write-dates-as-timestamps=false)
   - LocalDate used for date-only fields (dueDate, startDate, etc.)

7. FILE STORAGE:
   - Documents stored in MinIO bucket: workhive-documents
   - Files referenced by file_path in documents table
   - Max upload size: 50MB
   - Content types preserved for proper download headers

8. .ENV LOADING:
   - WorkHiveApplication.loadDotEnvIfExists() loads .env at startup
   - Searches: ".env", "../.env", "c:/workhivenew/.env"
   - Sets Java system properties (not environment variables)

9. DATABASE URL NORMALIZATION:
   - DatabaseUrlEnvironmentPostProcessor handles various cloud DB URL formats
   - Converts postgres:// and postgresql:// URLs to jdbc:postgresql://
   - Extracts username/password from URI userInfo

10. JACKSON SERIALIZATION:
    - Non-null property inclusion (null fields omitted from JSON)
    - ISO date strings (not timestamps)
    - Entities are serialized directly to JSON (no separate response DTOs in most cases)

11. EMPLOYEE CODE:
    - Auto-generated on user creation (e.g., "EMP-001")
    - Unique per tenant

12. INTEGRATION TOKEN ENCRYPTION:
    - Integration access/refresh tokens stored encrypted in DB (access_token_enc, refresh_token_enc)
    - AES encryption via CryptoUtils

13. OUTBOX EVENTS:
    - OutboxEvent entity for reliable event processing
    - Events published to outbox_events table
    - Background processor picks up and processes events

14. FLYWAY MIGRATIONS:
    - Enabled only in production profile (not dev)
    - Baseline-on-migrate: true (handles existing databases)
    - 6 migration files (V1 through V6)

18. KNOWN LIMITATIONS
==================================================

1. SEARCH: Global search is SQL LIKE-based, not full-text search or vector search.
   Performance may degrade with large datasets.

2. NO FULL-TEXT SEARCH: No PostgreSQL tsvector/tsquery or external search engine.

3. REDIS HEALTH CHECK DISABLED: Redis health check is disabled in application.yml.
   Redis failures may silently degrade performance.

4. MAIL HEALTH CHECK DISABLED: Mail health check is disabled. SMTP failures
   won't show in actuator health.

5. HARDCODED RENDER URL: Frontend client.ts has hardcoded Render URL fallback:
   'https://workhive-backend-zg37.onrender.com/api'. This is brittle.

6. NO RATE LIMITING IMPLEMENTATION: RateLimitException exists but no actual
   rate limiting middleware is implemented.

7. ENTITY SERIALIZATION: JPA entities are serialized directly as JSON responses
   in most controllers (no DTOs for responses). This exposes all entity fields
   including potentially sensitive data (password_hash is presumably excluded
   via @JsonIgnore or similar).

8. NO PAGINATION DEFAULTS ENFORCEMENT: Some frontend API calls use size=100
   or size=50, which could return large payloads.

9. NO WEBSOCKET AUTHENTICATION: WebSocket endpoint (/ws) is public.
   STOMP connections are not authenticated at the WebSocket level.

10. H2 DEV PROFILE: Dev profile uses H2 with ddl-auto=update which can
    cause schema drift from production PostgreSQL.

11. NO AUTOMATED TESTS IN CI: Test configuration exists (surefire plugin)
    but no CI/CD pipeline configuration found.

12. TYPESCRIPT STRICT MODE: TypeScript strict is set to false.
    Many types use 'any' in the frontend.

13. DOCUMENT STORAGE DEPENDENCY: Document features require MinIO to be running.
    No fallback for file storage.

14. INVITATION EMAIL: Email delivery depends on SMTP configuration.
    Email status tracking exists but failures may not be retried automatically.

15. NO API VERSIONING: API has no version prefix (e.g., /api/v1/).
    Breaking changes would affect all consumers.

16. TASK VERSION FIELD: Optimistic locking via version field exists but
    the frontend doesn't consistently pass version in all update requests.
